## Decision: transient-storage warning — evaluated and APPROVED, no code change
Manually audited `ReentrancyGuardTransient.sol` (OZ 5.6.1): `nonReentrant` always `tstore(true)`/`tstore(false)` per call, never sticks; EIP-1153 reverts undo transient storage same as normal storage within a call frame; no nested `nonReentrant` calls in `Crowdfunding.sol`; external `.call{value}` targets are EOAs (creator/backer), not reentrant into the contract before the guard clears. Conclusion: the warning's real risk case doesn't apply here. Kept `ReentrancyGuardTransient` (not classic `ReentrancyGuard`, which would cost ~2500-5000 more gas, critical for the 120k pledge limit).

## Wallet auth + daily limit (2026-07-10)
Added a second control layer on `/backend`: connecting + signing the wallet is now mandatory to upload anything, and **1 upload per IP per day**.
Flow: frontend requests a nonce (`POST /api/auth/nonce {address}`, 5 min TTL, one-time use) → user signs the message (off-chain, gasless, `useSignMessage`) → frontend sends `POST /api/auth/verify {address, signature}` → backend checks the IP's daily quota (429 if exhausted), verifies the ECDSA signature against the stored nonce via `viem.verifyMessage`, **always deletes the nonce** (valid or not — true one-time use, a captured signature can't be replayed), and on success issues an opaque 15-min session token. That token (`Authorization: Bearer`) authorizes `/api/pin-file`/`/api/pin-json` via `requireSession` middleware — 401 without it, the Pinata JWT is never exposed to unauthenticated callers.
Limit lives in one place, `backend/src/config.ts`: `MAX_UPLOADS_PER_IP_PER_DAY = 1` (plus `NONCE_TTL_MS`, `SESSION_TTL_MS`).
**Known unresolved limitations:** in-memory quota counter (a `Map`) resets on backend restart/doesn't share across instances; per-IP limiting is imperfect (NAT/VPN); doesn't change Pinata's real 1 GB cap.
